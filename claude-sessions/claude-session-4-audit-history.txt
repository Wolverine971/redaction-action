⏺ I haven't changed anything yet. Most of this already exists, but the history breaks in a few places, so I have a couple of questions before I build.
  
  **What already works:** every redact or keep decision is logged with the reviewer's name, the time, and the before → after state. Nothing edits those log entries.
  
  **Where history gets lost:**
  1. **Re-running detection** deletes every entity and decision. The old log entries stay, but they point at entities that no longer exist. The name and the decision survive only inside a sentence of text.
  2. **Merging two entities** deletes one of them. Its decision (say, "kept by Priya at 3:15") isn't saved with the merge. Its mentions then switch to the other entity's decision, and nothing logs that.
  3. **A mention's "decided by"** is overwritten when someone later confirms who the mention refers to, so it can name the wrong person. The export's redaction log just says "reviewer" instead of a name.
  4. **The UI has no per-entity history.** The review screen shows only the latest decision, and the report page shows one long list of every event.
  5. **Nothing stops edits to the log.** "Never edited" is just how the code behaves today; the database doesn't block changes.
  
  **Two versions:**
  - **Lean:** a proper decision history, with who, when, the change from → to, and a saved copy of the name. Every change writes to it at the same moment it happens, including merges and re-runs. The database refuses edits and deletes to it. Each entity gets a history timeline on the review screen, and the export gets a decision-history file.
  - **Ambitious:** everything in lean, plus re-running detection stops wiping work. Decisions carry over to the newly found entities with the same name, and each one is logged as "carried over from DJ's decision, Oct 30 3:04 PM".
  
  **Describe what you're envisioning for this history. Who's going to look at it, and where?** And do you want lean or ambitious? Unless you say otherwise, "who" stays the reviewer's typed name, with no logins.

❯ Yeah, go with the ambitious version. I like the audit trail to be like this: entities identified, and then, for each entity, which ones were in the history of each entity.
  
  If it was manual, for each entity, it should show the latest status and the history of it before. There should be a list of all the places that it's mentioned on the pages. If, for some reason, you allow one entity to be shown on page 3 of something, it would say that that was allowed or not allowed.
  
  It only gets complex if there are special cases, like when you allow certain references of a person through while you let certain references not through. That's where it gets a little complicated. In that case, it should show all instances of a person being allowed, all instances of the person not being allowed or being redacted.
